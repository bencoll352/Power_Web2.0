# Capture reproduction

All images are from normal running application interfaces. No screenshot-only UI, injected fake records, external provider dispatch or real customer/candidate data is used. Records are created through supported registration/API fixtures or normal application forms; the critical outcomes are exercised through real controls.

Use Node 24, Chromium and Playwright. Sales and CRM already declare their browser dependencies. Dependency-free products can use an external Playwright installation by setting `PLAYWRIGHT_MODULE` to the absolute path of `playwright-core/index.mjs`; no production browser package is added to them. All runners use en-GB locale, desktop 1440 × 1000 and mobile 390 × 844. Details use the actual dialog crop or a scrolled screen. PNG masters are under `masters/`; WebP copies are `dist/assets/product-screens/` from repository root.

Follow each owning repository's `docs/POWER-UP-SUITE.md` and `scripts/capture-suite.mjs` for the exact steps. Run one workflow at a time with fresh isolated demo databases. In particular, Communications and Business CRM both use port 5173; stop one before running the other. Never run fixture scripts against a real workspace.

1. Sales: install locked packages, use `DATA_DIR=/tmp/fresh-sales-suite PORT=3100 npm run dev`, run its capture script. Register labelled workspace, create four synthetic trade prospects and two overdue quotes; record accepted through the UI, verify queue 3 → 2 and reload, restore only that synthetic fixture for the image. Generate actual sample handover and marketing files with `scripts/export-suite-fixtures.mjs`.
2. CRM: local PostgreSQL, migrations and synthetic seed; run Business 5173/4101 and Personal 5174/4102. Capture runner registers a new UK trade Business workspace with four accounts and three follow-ups, including booked renewal review. Personal uses the separate documented synthetic account. Six images maintain separation.
3. Communications: build and run documented loopback development identity. Add synthetic company and sandbox enquiry, release assignment, take ownership, save callback and due time. Captures show sandbox, never live provider evidence.
4. Delivery: start server from a new temporary working directory so its `.data/delivery.sqlite` is isolated. Upload included Sales export through the form; enter scope/owner/start and confirm won; inspect stored record and reload. Captures retain pilot label. The capture file and Automation export are different authentic sample Sales exports, so isolate their runs to reproduce each view cleanly.
5. Automation: run `scripts/record-pilot.mjs` against a separate fresh Delivery database; it records actual create/duplicate/rejected/unconfirmed results. Use `AUTOMATION_RUNS_FILE=fixtures/pilot-log/runs.ndjson AUTOMATION_SAMPLE_DATA=1 npm start`. View and capture without executing from the viewer. If a record already exists, its genuine receipt will say already_exists; never forge created.
6. AI Team: new empty `TEAM_DB`, documented synthetic bootstrap token, `TEAM_INLINE_WORKER=1 node team/server.mjs`; run capture script. Create employee, approve sample company text, assign brief, inspect citation, revise and accept. Mobile/detail frames scroll to evidence and review. This is generic trade research, not the separate recruitment app.
7. Marketing: static server on 3400; load included `sample-sales-outcomes.json` through normal file input, compare campaign groups and inspect detail. Two named campaigns and unattributed prospects remain visible. Invalid JSON error is checked.

Website: `npm run build`, `npm run check`, `npm start`; run `tests/site-browser.mjs` with `PLAYWRIGHT_MODULE` and `CHROMIUM_PATH=/usr/bin/chromium` when using external browser tooling. Static local URLs use `.html`, matching the links. Firebase configuration supplies clean public routes. Screenshot browser checks decode every mobile source and request every detail image, in addition to the full existing responsive/navigation/demo checks.
